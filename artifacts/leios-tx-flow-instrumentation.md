# Collecting transaction-flow data from a musashi relay

**Provenance:** ⏳🤖 LLM-generated, pending human review · **Layer:** implementation and deployed configuration · **Verified:** 2026-09-21

> [!NOTE]
> **Method.** The namespace inventory, severities, and visibility verdicts below
> were generated by the **w36 node binary itself** — the build musashi runs —
> against our pinned `config.json`:
>
> ```shell
> cardano-node trace-documentation --config config.json \
>   --output-file traces.md --output-metric-help metrics.json \
>   --output-namespace-list namespaces.txt
> ```
>
> 650 namespaces, 143 metrics. So "Invisible @Notice" below is not a guess about
> some default config; it is what *your* config does. Re-run it after any config
> change. Companions: [the lifecycle diagram](./leios-node-tx-lifecycle.svg) for
> what the stages are, [the mempool/TxCache map](./leios-node-mempool-txcache.md)
> for how they work, [the metrics mapping](./leios-mempool-metrics-mapping.md)
> for what the quantities mean, [the tooling note](./leios-node-tooling.md) for
> the tools.

## The short version

Four stages, four observation surfaces, and one surprise:

| Stage | Surface | State in the shipped config |
|---|---|---|
| **Push** — transactions arriving from peers (N2N tx-submission) | `TxSubmission.TxInbound.*`, `TxSubmission.Remote.*` traces | **Entirely invisible.** All at `Debug`, filtered at `Notice`. |
| **Local submission** — anything you or a tool submits | `TxSubmission.Local.*`, `TxSubmission.LocalServer.ReceivedTx` | **Invisible.** Same reason. |
| **Mempool** — accept, reject, evict, re-sync | `Mempool.*` traces + EKG/Prometheus gauges | **Partly on**: `AddedTx`, `RejectedTx`, `RemoveTxs` visible; `AttemptAdd` and `SyncNotNeeded` explicitly `Silence`d; `Synced` at `Debug`. |
| **Cache and EB closure** — the pull side | `Consensus.LeiosKernel.*` traces + the LeiosDb SQLite file | **On**, at `Debug` with no rate limit. |

The surprise is the first two rows: the pinned musashi config turns the whole
transaction-arrival path off. Anything you want to say about *push* volume, pull
requests, or per-peer arrival needs a config change first. The Leios side, by
contrast, is already fully traced.

## 1. What each surface gives you

### 1.1 Push and pull of transactions between peers

N2N tx-submission is **pull-based**: a node asks for tx *ids*, then asks for the
bodies it wants. The inbound accounting is the interesting half.

| Namespace | Severity | What it carries |
|---|---|---|
| `TxSubmission.TxInbound.Collected` | Debug | "Number of transactions just about to be inserted." |
| `TxSubmission.TxInbound.Processed` | Debug | "Just processed transaction pass/fail breakdown." |
| `TxSubmission.TxInbound.AddedToMempool` | Debug | "Transactions added to the mempool and processing time" |
| `TxSubmission.TxInbound.RejectedFromMempool` | Debug | Rejections, with processing time |
| `TxSubmission.TxInbound.RequestTxs` | Debug | Transactions requested from the remote peer |
| `TxSubmission.TxInbound.{Can,Cannot}RequestMoreTxs` | Debug | Credit-window state — why the node is or isn't asking for more |
| `TxSubmission.Remote.{Send,Receive}.{RequestTxIds,ReplyTxIds,RequestTxs,ReplyTxs}` | Debug | The raw mini-protocol messages, per peer |
| `TxSubmission.TxOutbound.{RecvMsgRequest,SendMsgReply}` | Info | The serving side: what *we* hand to downstream peers |

`Remote.*` traces carry the peer's `connectionId`, so they are the only way to
get **per-peer** arrival — which is what a fragmentation question ultimately
needs. They are also the highest-volume traces on this list.

### 1.2 Mempool

Traces: `Mempool.AddedTx` and `Mempool.RejectedTx` (Info, **already on**),
`Mempool.RemoveTxs` (Info — txs invalidated by a ledger change),
`Mempool.ManuallyRemovedTxs` (Warning), `Mempool.AttemptAdd` (Debug,
`Silence`d — the denominator for an accept rate), `Mempool.Synced` and
`Mempool.SyncNotNeeded` (Debug — re-sync after block adoption), and
`Mempool.TipMovedBetweenSTMBlocks` (Debug — a fork between two reads during
re-sync).

Metrics, sampled continuously and therefore the cheapest thing to record:
`txsInMempool`, `mempoolBytes`, `txsProcessedNum`, `txsSyncDuration` and
`txsSyncDurationTotal` (ms to re-sync after block adoption),
`txsMempoolTimeoutSoft` and `txsMempoolTimeoutHard`; plus `cumulativeTxBytes`
and `utxoSize` for chain-side context. The w38 build adds `mempoolCapacityBytes`
and a `Mempool.CapacityChanged` namespace; **w36 has neither**, so on the build
you are running capacity is not a metric — read it from
`cardano-cli dijkstra query tx-mempool info`.

### 1.3 The cache and the EB closure — the Leios side

Already at `Debug` with `maxFrequency: 0`, so this needs no config work. The one
to build on:

**`Consensus.LeiosKernel.BodyHits`** — emitted once per EB body inserted into
the LeiosTxCache, *after* the mempool pull, precisely so it can attribute the
EB's transactions to their sources in a single record:

```
kind, ebHash, ebSlot, txsInEb, tracked, acquired, validated,
mempoolHits, missedBoth, cacheTxCount, cacheLoad
```

with `txsInEb ≥ tracked ≥ acquired ≥ validated` (the nesting is a documented
contract on `LeiosTxCacheInsertBodySummary`). So for every EB: `validated` /
`acquired` is what the cache already held, `mempoolHits` is what the local
mempool supplied, `missedBoth` is what must be pulled over `LeiosFetch` —
**the per-EB fragmentation measurement, already instrumented** — with
`cacheLoad` (cache occupancy as a fraction of worst-case capacity) as the
pressure covariate.

Supporting traces:

- `FetchBodyArrival` / `FetchTxsArrival` (Debug) — byte accounting with a waste
  classification, and the only namespaces in the Leios set that declare
  metrics: `leiosFetchBody{Good,Extra,Evicted,Invalid}Bytes` and
  `leiosFetchTxs{Good,Extra,Evicted,Invalid}Bytes`. `Good` is the expected case,
  `Extra` redundant (already held), `Evicted` arrived after the cache dropped
  its announcement, `Invalid` failed validation. `Extra / (Good + Extra)` is a
  duplicate-fetch ratio.
- `BlockAcquired` / `BlockTxsAcquired` (Info) — `ebHash`, `ebSlot`, and
  `bodyAgeSeconds`: EB body and closure arrival latency.
- `BlockPointMissing` (Warning) — an acquisition counter despite its name; see
  [facts.md](../facts.md). Useful only as a cross-check on `BlockAcquired`.
- `FetchDecision` (Info) — what the fetch logic decided, with peer counts and
  durations.
- `Db` (Info) — `leiosDbVolatileEbs`, `leiosDbImmutableEbs`, `leiosDbWalBytes`
  gauges; `Db.Copied` and `Db.Evicted` counters; `Db.CopyQueueFull`,
  `Db.CopyError`, `Db.SweepError` warnings.
- `LeiosFetch.Remote.*` and `LeiosNotify.Remote.*` — per-peer message traces.
  Note the pinned config **silences** `LeiosNotify.Remote.{Send,Receive}.Votes`
  and `.RequestNext`; the rest are at `Debug`.

> [!WARNING]
> **No `leios*` metric name appears in the binary's own metrics help or
> documented namespace list — in either build.** The Leios tracers do emit (your
> log has `Consensus.LeiosKernel.Db` lines), but they are absent from
> `--output-namespace-list` and `--output-metric-help`, so `trace-documentation`
> will not tell you about them and there may be no Prometheus gauge behind them.
> Settle it in five seconds on your node:
> `curl -s localhost:12798/metrics | grep -i leios`. Empty means the Leios
> numbers must come from the JSON traces rather than Prometheus. This also
> answers our standing question about `leios_logmetrics_*`: no such metric
> exists in these builds.

## 2. The config change

Traces are filtered by severity per namespace, so collection is a config edit
plus a restart. Edit `musashi/config/config.json` — **not** `data/` — since
`run-node.sh` re-copies the config on every start.

```shell
jq '.TraceOptions += {
      "TxSubmission.TxInbound":  {"severity":"Debug","maxFrequency":0},
      "TxSubmission.TxOutbound": {"severity":"Debug","maxFrequency":0},
      "TxSubmission.LocalServer":{"severity":"Debug"},
      "Mempool":                 {"severity":"Debug"},
      "Mempool.AttemptAdd":      {"severity":"Debug","maxFrequency":0},
      "Mempool.SyncNotNeeded":   {"severity":"Info"}
    }' config/config.json > config/config.json.new && mv config/config.json.new config/config.json
podman kube down musashi-relay.yaml && podman kube play musashi-relay.yaml
```

Then confirm what you actually enabled, rather than assuming:

```shell
podman exec musashi-relay-node cardano-node trace-documentation \
  --config /data/config.json --output-file /tmp/t.md --output-namespace-list /tmp/ns.txt
podman exec musashi-relay-node grep -A4 'Mempool.AttemptAdd' /tmp/t.md
```

Add `"TxSubmission.Remote": {"severity":"Debug","maxFrequency":10}` only when
you need per-peer message detail, and keep the frequency cap: on a synced relay
this is the loudest family on the node — two traces per message per peer.
`maxFrequency: 0` means *no limit*, not *no traces*; the pinned config uses it
deliberately for the Leios namespaces.

## 3. Where the data goes

1. **The log file you already have.** `run-node.sh` tees stdout to
   `${WORKING_DIR}/node.log`, appending across restarts with a
   `==== run started at … ====` marker per run. One JSON object per line:
   `{at, ns, data, sev, thread, host}`. Simplest, and entirely sufficient for
   after-the-fact analysis — but rotate it yourself, because nothing else will,
   and the volumes in § 2 are the reason to care.
2. **`cardano-tracer`.** The config already enables the `Forwarder` backend
   (`TraceOptionForwarder`), so a tracer process can receive traces over a
   socket instead of you scraping stdout. This is the structured path, and what
   the x-ray stack's Loki ingestion is built on.
3. **Prometheus** on `:12798`, once `pin-config.sh` has rebound it off
   loopback — for the continuously sampled gauges (`txsInMempool`,
   `mempoolBytes`, the sync durations) where a counter beats a log line. Names
   are prefixed per `TraceOptionMetricsPrefix` (`cardano.node.metrics.`) and
   mangled by the exporter, so match them against the endpoint rather than
   constructing them by hand.

## 4. Recipes against `node.log`

```shell
# The funnel in one pass: arrival → mempool → EB closure
jq -r 'select(.ns|startswith("TxSubmission.TxInbound") or startswith("Mempool.") or startswith("Consensus.LeiosKernel"))
       | .data.kind' node.log | sort | uniq -c | sort -rn

# Where each EB's transactions came from (the fragmentation measurement)
jq -r 'select(.data.kind=="LeiosBodyHits")
       | [.data.ebSlot, .data.txsInEb, .data.validated, .data.mempoolHits, .data.missedBoth, .data.cacheLoad]
       | @tsv' node.log

# …and the aggregate: cache share, mempool share, pull share
jq -s '[.[]|select(.data.kind=="LeiosBodyHits").data]
       | {ebs: length,
          txs:         (map(.txsInEb)     | add),
          fromCache:   (map(.validated)   | add),
          fromMempool: (map(.mempoolHits) | add),
          pulled:      (map(.missedBoth)  | add)}' node.log

# EB body and closure arrival latency
jq -r 'select(.data.kind=="LeiosBlockAcquired" or .data.kind=="LeiosBlockTxsAcquired")
       | [.data.kind, .data.ebSlot, .data.bodyAgeSeconds] | @tsv' node.log

# Mempool traffic by kind (AttemptAdd gives the accept-rate denominator)
jq -r 'select(.ns|startswith("Mempool.")) | .ns' node.log | sort | uniq -c
```

`LeiosBodyHits` is per **EB**, not per transaction: it says how many of an EB's
transactions each source supplied, never which ones. Per-transaction provenance
needs either the `ebTxs` table joined against your own arrival log, or the
color-tagging approach in § 6.

## 5. The LeiosDb, for state rather than events

The SQLite store answers "what does this node hold now" where the traces answer
"what happened". Schema, caveats, and the EB-overlap query are in
[the tooling note](./leios-node-tooling.md) § 3.2 — including the correction
that `ebs` rows come only from body acquisition, so it samples EBs this node
*fetched*, not EBs it was told about.

## 6. When passive observation is not enough

Tracing a live testnet tells you what its traffic happens to be. To *set* the
traffic, the release ships `tx-firehose` (push load over the local socket, with
`--color` tagging each transaction in metadata label 1022) and `mempool-monitor`
(one per node, tallying those colors over `LocalTxMonitor`). That pair turns
"how fragmented are mempools" from an inference into a controlled measurement —
see [the tooling note](./leios-node-tooling.md) § 4 for the caveats, especially
that the observer costs one round trip per transaction and that capacity is
reported in bytes while a validation-time dimension binds first.

On musashi this needs funded keys and is polite to coordinate; on a local
`dozen-devnet` it needs neither.

## 7. Known limits of this surface

1. **Per-peer transaction arrival requires the loudest traces on the node**
   (`TxSubmission.Remote.*`), and per-transaction source attribution is not
   traced at all — only counted.
2. **`LeiosBodyHits` is per EB**, so cache/mempool/pull shares are aggregate
   per EB body.
3. **No Leios Prometheus metrics are documented** in either build (§ 1.3), so
   Leios series must be derived from logs.
4. **Votes and certificates are trace-only**, absent from the LeiosDb, with no
   local-state query.
5. **Mempool capacity is one dimension.** On w36 it is not even a metric, and
   the validation-time dimension that binds first on the prototype is exposed
   nowhere.
6. **Everything here is one node's view.** Diffusion questions need several
   nodes, which is what makes a local devnet or a coordinated multi-node run the
   natural next step.
