- **The post-CIP memory-pool simulator hardcodes uniform-random transaction time and ingress node, while its public event API already accepts an explicit time and node** (verified by source reading 2026-09-24; layer: simulator @ `ouroboros-leios` [`f65db01`](https://github.com/input-output-hk/ouroboros-leios/tree/f65db01ca1f9462241e844bd3018cc4b78d41a30/post-cip/mempool-sim-web)): the command-line driver chooses `nodeIndex = floor(random × honestCount)` and `time = txDuration × random` for every transaction, and the model card explicitly says real arrivals are bursty and concentrate at popular endpoints. The core `SubmitTx` event and `submitTx` method take an explicit `clock` and `nodeIdx`, so alternative ingress policies need a new driver and an explicit gateway layer, not a replacement gossip engine.

- **Lifecycle-audit implementation facts** (verified by source reading during the 2026-09-17 accuracy review of the [transaction-lifecycle diagram](./artifacts/leios-node-tx-lifecycle.svg); layer: implementation @ ouroboros-consensus `b56977b`):
  - The **minimum certification gap is a minimum wait** (`currentSlot − announcementSlot ≤ minGap ⇒ Nothing` in `decideLeiosCertify`), and certification must occur in the announcing RB's direct successor — so a successor RB elected *inside* the gap strands the pending EB. Enforcement is **forge-side only**: follower validation carries `FIXME: Check the min certification gap` (`Forker.hs:618`), with no other validation-side use of `getMinCertificationGap`.
  - A **CertRB's wire body carries the Leios certificate and no regular transactions** (`mkBody`: tx sequence `Seq.empty`, certificate via `leiosCertBlockBodyL`); "empty body" comments are shorthand.
  - **Missing-closure CertRB parking is implemented**: `ignoreUnacquiredCertRB`/`...Suc` transiently hide a CertRB and its successors from chain-selection candidates until the closure arrives; `leiosAcquiredEbsRunner` + `chainSelReprocessLeiosEb` reprocess on `AcquiredEbTxs`.
  - **Fetch priority is two-tiered** (`fetchPriorityTiers`): EBs within L = 3·L_hdr + L_vote + L_diff of the current slot are requested oldest-first, staler EBs then freshest-first; slot unknown (syncing) ⇒ one oldest-first tier.
  - **Vote timing is wall-clock-stubbed**: window opens at announced-slot onset + `lHdrWait = 3 s`, deadline + `lVoteWindow = 4 s` later (both TODO-marked to become ledger protocol parameters); the check runs immediately if the closure completes after the window opens.
  - **Fetching is incremental, but voting validation is whole-closure gated rather than streamed**: fetched transaction jobs are inserted as they arrive, while `runLeiosVoting` schedules an EB only after LeiosDb emits `AcquiredEbTxs`; `validateEbClosure` then resolves and classifies the complete closure before serial application. The source explicitly lists validation during streaming as a TODO (verified 2026-09-23; layer: implementation @ `b56977b`).
  - The ≤ 2-announcements-per-election limit is enforced per upstream peer by `PeerState`/`ElState` (third or repeat ⇒ disconnect); `ElBimap` is the downstream relay gate for equivocation evidence.
  - **Offer gating is two-level**: LeiosDb emits `AcquiredEb` on body insert (→ `MsgLeiosBlockOffer`) and `AcquiredEbTxs` only on closure completion (→ `MsgLeiosBlockTxsOffer`); a completed SQLite row stores `missingTxCount = −1` as the notified sentinel.
  - Mempool `Sync` is bounded by a **converging off-lock catch-up loop** (`syncDeltaCap = 256` under-lock target, `syncMaxIters = 8` safety valve); `reapplyUntilTimeout` bounds *snapshot* computation, not `Sync`. Default mempool capacity is 2× the ordinary block measure, byte-overridable; the CIP's ≥ 2 × (RB+EB) formula awaits `ouroboros-consensus#2280`.
  - **Certified closure adoption skips transaction validation but remains serial**: [`resolveAndApplyLeiosClosure`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/LedgerDB/Forker.hs#L948-L985) batches the closure's UTxO ledger-table key read, then [`applyLeiosClosure`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Leios.hs#L158-L218) uses a sequential `foldM` over the Dijkstra `LEDGER` rule with `ValidateNone`, so transaction signatures and Plutus scripts are not rechecked. The certificate licenses that trust. The prototype does not implement the post-CIP constraint model's input-DAG antichain scheduler; voting's [`validateEbClosure`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus/src/ouroboros-consensus/LeiosVoting.hs#L1981-L2160) is also a serial apply/reapply recursion (verified 2026-09-23; layer: implementation @ ouroboros-consensus `b56977b`).
  - Demo fetch-job caps: `maxJobBytesSize = 64 KiB`, `maxJobTxCount = 20000`. LeiosDb EB statuses are not one linear chain: certified 0→1→2, cleanup 0→3 and 2→3, and promotion rescues 3→1.
  - Two source comments are **stale at this very commit**: ChainSync announcement folding *is* wired (`leiosMsgRollForwardCallback` → `processAnnouncementCentrally ReceivedViaChainSync`), and "proper EB announcements not implemented" reduces to body-size validation still trusting request/offer-carried state.

## Protocol Parameters

- **The Leios parameter set is nine Dijkstra ledger protocol parameters** (verified 2026-09-17 by source reading at cardano-ledger `1587f21`, the node's exact build pin; layer: implementation): `leiosAnnouncementPeriodLength`/`leiosVotePeriodLength`/`leiosDiffusionPeriodLength` (Milliseconds32 — L_hdr/L_vote/L_diff), `leiosCommitteeSize` (Word16, N_c), `leiosQuorumStakeThreshold` (UnitInterval, τ), `maxEndorserBlockReferencesSize`/`maxEndorserBlockTxsSize` (Word32 bytes), `maxEndorserBlockExUnits`, `maxRefScriptSizePerEndorserBlock` — all on-chain-governable, all in the NetworkGroup/SecurityGroup update groups. `maxKeyAge` for voting keys is deliberately *derived* (⌈KES lifetime in epochs⌉ + 2), not a parameter.
- **There is no maximum transaction-DAG span parameter in the current public design or prototype** (verified 2026-09-23; layer: model and implementation): the pinned Dijkstra [`PParams`](https://github.com/IntersectMBO/cardano-ledger/blob/1587f21a7d1306dc590c2749a5c66232ef66aad0/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/PParams.hs#L199), the [ledger implementation ticket's parameter list](https://github.com/IntersectMBO/cardano-ledger/issues/5965), and the [post-CIP constraint model](https://github.com/input-output-hk/ouroboros-leios/tree/main/post-cip/constraint-model) contain no parameter or admission rule bounding the longest intra-block transaction-dependency chain. The model schedules over an input DAG and reports critical-path behavior but does not constrain its span. This establishes public-source absence, not that the idea was never discussed privately.
- **Deployed musashi values** ([`dijkstra-genesis.json`](https://book.play.dev.cardano.org/environments-pre/leios/dijkstra-genesis.json), [`shelley-genesis.json`](https://book.play.dev.cardano.org/environments-pre/leios/shelley-genesis.json), and [`config.json`](https://book.play.dev.cardano.org/environments-pre/leios/config.json) fetched 2026-09-17; layer: deployed network — **weekly redeploys, re-fetch before use**): L_hdr/L_vote/L_diff = 1000/4000/7000 ms; N_c = 900; τ = 0.75; the 100 kB EB-reference parameter becomes a count ceiling of 2,777 transactions but does not itself guarantee an encoded reference list ≤ 100 kB; closure ≤ 1 MB; EB ExUnits 310 M mem / 100 G steps; ref-scripts ≤ 4 MB; slot 1 s, epoch 21,600 slots, f = 0.05, k = 108. The node requests `MempoolCapacityBytesOverride` = 2,000,000 B, which rounds to a 2,072,576 B effective byte coordinate at the 90,112 B block capacity. **Derived min certification gap = ⌈14,000 ms / 1 s⌉ = 14 slots**, conflicting with the Aug-2026 Slack claim of 10 ❓🤖 (unreconciled — weekly redeploys may have changed the periods, or "10" conflated the `fetchPriorityWindowSlots` constant, whose own comment says "~14 s on mainnet, ~10 on the testnet"). File hashes and configuration genesis hashes are recorded in [the parameter note](./artifacts/leios-node-protocol-parameters.md#sources).
- **Quorum mechanics** (layer: implementation @ pins above): seat weight = pool's share of total active stake (`Weight = Rational`, committee weights sum ≤ 1); vote acceptance tallies `totalW ≥ threshold` with re-votes replacing; `verifyLeiosCert` enforces bitfield well-formedness, rejects any signer bit on a keyless seat, requires `Σ seatWeight ≥ τ`, and verifies one aggregate BLS12-381 min-sig signature — matching CIP-0164's `Σ stake(votes) ≥ τ·stake_total-active`. Committee = **top-N_c pools by stake, deterministic** (CIP-0164 "stake-based truncation"; weighted Fait Accompli with Local Sortition (wFA^LS) is explicitly the earlier-drafts scheme), seated by the ledger SNAP rule on the mark snapshot for epoch e+1; keys honored while `epoch < registeredIn + maxKeyAge`.
- **Certificate aggregation is aggressive and freezes the first threshold-crossing signer set** (verified 2026-09-23; layer: implementation @ consensus `b56977b`): [`LeiosVoteState.addVote`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus/src/ouroboros-consensus/LeiosVoteState.hs#L79-L179) calls `aggregateLeiosCert` immediately when its running received-vote weight first reaches τ and memoizes the result; post-threshold votes update the tally but do not rebuild the certificate. A forger later obtains that cached value through [`queryCert`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/NodeKernel/Forge.hs#L288-L356). Therefore a pool absent from an on-chain certificate did not necessarily fail to vote; it may have arrived after quorum at that node.
- **Musashi routine voting found 62.18% of EB transaction references in the mempool and actively fetched 26.38%** (verified 2026-09-23 from `musashi/musashi-bp.log.gz`, SHA-256 `87bffbb…a192`; layer: deployed-node telemetry, image `prototype-2026w36`, consensus `b56977b`): over the 293 closures that completed voting validation, 379,884 of 610,924 reference occurrences were mempool-resident when their EB bodies were processed; 69,900 (11.44%) were cache-only, so 449,784 (73.62%) were locally available from the union, and 161,140 (26.38%) were in neither and formed the active fetch set. Mempool and cache counts overlap and must not be added directly. None of the canonical parents of the capture's four locally forged RBs announced an EB, so the sample size for acquisition/validation of a parent EB before this node's forge is zero; the routine-voting result cannot yet be compared with that cohort.
- **The public Go and Rust alternatives do not implement parallel transaction-DAG ledger application** (verified 2026-09-23; layer: implementations): Blink Labs Dingo `cde295a9` parallelizes Leios fetching across connections and has a DAG mempool, but documents that DAG as ordering/selection only and applies certified transactions in sequential loops; its current vote path signs on slot-verified EB acquisition without transaction ledger validation. Amaru `5a2a08bc` has no Leios implementation on main, and its sole public Leios workshop branch `12a7aded` only logs opaque LeiosNotify messages; the ordinary Amaru ledger serializes requests on one thread and block transactions in order, while using Rayon for independent header checks and within-transaction Plutus scripts. This cross-language evidence does not support Haskell purity as the principal cause of the prototype's serial closure path; see the [source audit](./musashi/observations.md#cross-language-check-serial-closure-application-is-not-specifically-a-haskell-artifact).
- **Enforcement asymmetry** (layer: implementation; the sharpest finding): the honest forge precisely enforces transaction bytes, execution units, and reference-script bytes, but reduces `maxEndorserBlockReferencesSize` to a transaction-count ceiling using the minimum 36 B encoded entry; the count ceiling does not guarantee the actual encoded reference list satisfies the byte limit. The forge-side certification gap in `decideLeiosCertify` and the voter's stubbed 3 s/7 s window are implemented, but the Byzantine-facing acceptance checks are FIXME/TODO — no ledger rule consumes the EB-cap parameters, `Forker.hs:618` skips the gap, and `Praos.hs:526` TODO-lists five unimplemented header checks (`LeiosCertRBWithoutAnnouncement`, `LeiosCertTooYoung`, `LeiosEbTooBig`, `LeiosEbTxsTooBig`, `LeiosEbCertExclusivity`). The one fully-enforced acceptance rule is the certificate's quorum + signature verification. Votes are not epoch-tagged (TODO) and certs are not committee-tagged (FIXME). Wire clamping: governance can raise EB caps past the 500 kB / 12 MB wire constants and "nothing rejects that today." Details: [the protocol-parameter note](./artifacts/leios-node-protocol-parameters.md).
- **The forge's certification gap is one slot stricter than CIP-0164** (verified 2026-09-17 by source reading; layer: implementation @ consensus `b56977b` vs CIP `d07a30b`). The CIP admits a certificate when `slot(RB′) − slot(RB) ≥ gap`; `decideLeiosCertify` guards `elapsed ≤ minGap ⇒ Nothing` ([`Forge.hs:322`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/NodeKernel/Forge.hs#L322)), so it certifies only at `≥ gap + 1`. The EB point carries the announcing RB's slot, so the comparison is like-for-like. Consequence for skip-rate modeling: the at-risk window is `gap` slots under the implementation (1 − 0.95¹⁴ ≈ 51.2% stranded at f = 0.05) but `gap − 1` under the CIP (≈ 48.7%). **Caution:** the CIP quotes 0.95¹³ ≈ 51% for no intervening RB, hence EB survival under that model; that is the complement of the ≈51% skip figure in our notes. Not recorded in source as deliberate ❓🤖.
- **Two CIP-0164 vote conditions are absent from the prototype voter, while a third is enforced incidentally outside voting** (verified 2026-09-17; layer: implementation @ `b56977b`): (1) "the RB header arrived within L_hdr" is not checked for voting; announcement age separately controls 5-minute relay and 10-minute receive guards and supplies body/closure telemetry, but neither guard compares with L_hdr. (2) "no equivocating RB header for the slot" is detected per peer by `PeerState`/`ElState` (and the peer disconnected), but `AnnouncementEquivocation` is consumed only for tracing, `goVote` never consults it, and `LeiosNotVotedReason` has no such constructor, even though `lHdrWait` exists as the observation window. (6) "the EB contains at least one transaction" is not a vote rule; it is enforced incidentally because `leiosDbInsertEbBody` calls `error "empty EB body (programmer error)"`, reached on the per-peer LeiosFetch thread, so an empty peer EB drops that peer. Conditions 3 (deadline, from stubs), 4 (`tipAnnouncerFor`) and 5 (`validateEbClosure`) are enforced by the voter.
- **Received votes face no timing check** (verified 2026-09-17; layer: implementation @ `b56977b`): `LeiosVoteState.addVote` checks dedup, committee seat, key and signature only, and `LeiosVote` carries `(announcingRbHash, voterId, voteSignature)` — no slot, no timestamp — so the voting window cannot be checked at ingest without a chain lookup. The window is honest-node self-restraint; a tally can cross τ from late votes.

- **Pool-metadata limits, measured rather than quoted** (2026-09-22, against the w36 `cardano-cli dijkstra stake-pool metadata-hash`; layer: implementation): `name` ≤ 50 **characters** (50 Greek capitals = 100 bytes pass; 51 characters fail), `ticker` 3–5 characters (Greek accepted by this validator, though the off-chain registry convention is `[A-Z0-9]{3,5}`), `description` ≤ 255 characters, `homepage` **unbounded** by the validator despite the usual "≤ 64" claim, and the whole file ≤ **512 bytes** — the only byte-denominated field limit. The certificate's metadata **URL** limit is **128 bytes** on this network, not 64: `Url`'s `decCBOR` takes `textDecCBOR 128` from protocol version 9 onward and 64 before ([`BaseTypes.hs:679-686`](https://github.com/IntersectMBO/cardano-ledger/blob/1587f21a7d1306dc590c2749a5c66232ef66aad0/libs/cardano-ledger-core/src/Cardano/Ledger/BaseTypes.hs#L679)), and musashi runs version 12.
- **`cardano-cli` can hash pool metadata over `file`, `http`, `https`, and `ipfs`, with the IPFS gateway supplied by environment** (verified 2026-09-22 by running all four paths): `ipfs://` without `IPFS_GATEWAY_URI` fails with a message naming the variable, and with it set the CLI requests `<gateway>/ipfs/<cid>`. `https://ipfs.io` answers that path with **HTTP 429** and a notice that it is "switching to a service worker gateway only", so public path-style gateways are not a safe default. The on-chain hash is blake2b-256 of the file's bytes and is independent of the CID, so `--expected-hash` verification works over any scheme.
- **The BLS key's registration is verifiable in the certificate's CBOR** (verified 2026-09-21 by generating a real pool registration certificate with the w36 CLI and decoding it): the 11-element `stake_registration` structure carries, after the pool and VRF key hashes, a **`list(2)` of a 96-byte and a 48-byte bytestring** — the BLS12-381 **min-sig** public key (G2, 96 B compressed) and its proof of possession (G1, 48 B), matching `BlsKey { blsPubKey, blsPossessionProof }` over `BLS12381MinSigDSIGN`. So "the Leios voting key is registered through the pool certificate" is now confirmed end to end, from CLI flag to encoded certificate, not only from ledger types.

Both would put a node on the wrong chain instance today. Worth reporting upstream alongside the `BlockPointMissing` item.
- **Cardano addresses do not distinguish one testnet from another** (verified 2026-09-21 by building the same key's address at magics 1, 2, 42, and 164 with the w36 CLI): all four are byte-identical (`addr_test1qru6dedvx…`), and only the mainnet form differs; stake addresses likewise. So a preprod/preview address is a valid musashi address, funds at it are chain-local, a wrong-network send cannot bounce, and a stake key registered on another testnet is unregistered here.
- **Musashi's pool economics and rotation clocks** (read 2026-09-21 from the pinned `shelley-genesis.json`; layer: deployed network — governable, so confirm with `query protocol-parameters`): `poolDeposit` **500 ₳**, `keyDeposit` **2 ₳**, `minPoolCost` **170 ₳** (a floor on `--pool-cost`), `minUTxOValue` 1 ₳, fees *a* = 44 / *b* = 155,381. Epochs are 21,600 slots at 1 s = **6 hours**, so stake delegated in epoch *N* is active at the start of *N+2* — a wait of **6–12 hours** from an arbitrary point in epoch *N* — and Leios committee seating uses the same snapshot boundary. Two rotation clocks coincide at ≈93 days: Key Evolving Signature (KES) (`maxKESEvolutions` 62 × `slotsPerKESPeriod` 129,600 s) and the Boneh–Lynn–Shacham (BLS) key (`maxKeyAge` 374 epochs), but renewing the BLS key means **re-registering the pool**, not reissuing a certificate. `cardano-node` checks only the **verifiable random function (VRF)** signing key's file permissions at startup (`checkVRFFilePermissions`, rejecting any group or other permission), not KES.
- **Pool ΘΕΛΩ activation state** (verified 2026-09-22 from the submitted registration and faucet delegation; layer: deployed musashi network): pool `88610017a37cfcbf497127b1be43efd71376bd52f3bb8773b3dcf838` registered and received its faucet delegation in epoch 62; the producer pod is deployed, and the stake becomes active at the start of epoch **64**, 2026-09-23 00:00 UTC. Activation makes the pool eligible for Praos leadership and Leios committee participation; it does not guarantee a block-production slot.
- **A pool's Leios voting key is registered through its pool registration certificate, not a separate transaction** (verified 2026-09-21 by source reading at cardano-ledger `1587f21`; layer: implementation): `sppBlsKey :: StrictMaybe BlsKey` on [`StakePoolParams`](https://github.com/IntersectMBO/cardano-ledger/blob/1587f21a7d1306dc590c2749a5c66232ef66aad0/libs/cardano-ledger-core/src/Cardano/Ledger/State/StakePool.hs#L460-L472), where `BlsKey = { blsPubKey, blsPossessionProof }` over BLS12-381 min-sig. The ledger keeps `BlsKeyState { bksKey, bksRegisteredIn }`, the epoch stamp that the `maxKeyAge` (374-epoch) expiry is measured from. On the node side the operator supplies the signing key with `--shelley-bls-key` ([`Parsers.hs:420`](https://github.com/IntersectMBO/cardano-node/blob/7e33674108ed17eeeda3a25e98b66a610cbd99ff/cardano-node/src/Cardano/Node/Parsers.hs#L420), "Path to the BLS (Leios) signing key").

- **The musashi chain runs the w36 build, and a newer weekly image silently diverges from it** (diagnosed 2026-09-21 from a stalled relay's log plus registry and `flake.lock` comparison; layer: deployed network vs release artifact — **the operational trap of the prototype**): a relay on `prototype-2026w38` synced for days, then rejected the block at slot 854,400 (`19067ce95067…`) **34 times in 54 seconds**, once per peer, with `ValidationTagMismatch Phase2Valid (FailedUnexpectedly (PlutusFailure …))` on transaction `ca42eb12…`, PlutusV4 script `603320d0…` — the producer marked the transaction phase-2 valid and our node's evaluation said the script failed. All five bootstrap relays were then at slot 1,268,908 (block 57,111), ~4.8 days past the rejected block, so the network accepted it and the node was alone. Cause: the image is built from `cardano-node` `648fc48b` (w38), whose `cabal.project` moved **cardano-ledger from `1587f21a` to `daa38fec`** relative to w36 (`afa091b4`) — the build the chain was deployed from, per the live `MinNodeVersion` `11.1.0.164-prototype-2026w36` and the w36 image's 2026-09-07 build date, the day of `systemStart`. **Both builds report `cardano-node 11.1.0.164`**, so `--version` does not discriminate and `MinNodeVersion` is only a floor. On a prototype branch the ledger changes without a hard fork, so *newer is not safer*: match the image week to the network. (That the block is genuinely valid under w36's rules is inferred from the network's agreement, not verified by re-validating it ❓.)
- **The Leios protocol-parameter update flags are a w38 addition** (verified 2026-09-21 by running both CLIs): `--leios-announcement-period-length`, `--leios-vote-period-length`, `--leios-diffusion-period-length`, `--leios-committee-size`, `--leios-quorum-stake-threshold`, `--max-endorser-block-{references-size,txs-size,execution-units}`, `--max-ref-script-size-per-endorser-block` are present in `648fc48b`'s `dijkstra governance action create-protocol-parameters-update` and **absent** in `afa091b4`'s. The `dijkstra node`, `dijkstra query`, and `dijkstra stake-pool` help output is byte-identical between the two builds, so the BLS findings hold for both. Parameter-variation experiments against musashi therefore wait on the network rolling to w38; a local devnet does not.
- **`cardano-cli` has a complete Leios surface, except for queries** (verified 2026-09-21 by running the binary; layer: implementation): `dijkstra node key-gen-BLS` / `key-hash-BLS` generate the Leios voting key; `dijkstra stake-pool registration-certificate` requires `--bls-signing-key-file` **unbracketed** — mandatory, and the *signing* key, because the certificate carries a proof of possession (the ledger's own field is `StrictMaybe`, so the CLI is stricter than the ledger); and `dijkstra governance action create-protocol-parameters-update` exposes all nine Leios parameters. But `dijkstra query` has 29 subcommands and **none is Leios-specific** — no committee-seating, EB, vote, or certificate query, and no `GetLeios…`-shaped local-state query exists at consensus `b56977b` either. `cardano-cli latest` is **Conway**, and the Conway forms of these commands silently lack the Leios options.
- **Changing any Leios parameter needs SPO votes, not just DRep votes** (layer: implementation; from upstream's [`propose-pparam-update.sh`](https://github.com/input-output-hk/ouroboros-leios/blob/9fa5a956db7a7860065b68e221c6f7ce647242d5/demo/dozen-devnet/propose-pparam-update.sh), 2026-09-21): every Leios parameter is declared `PPGroups 'NetworkGroup 'SecurityGroup` in Dijkstra's `PParams.hs`, so a change must clear `poolVotingThresholds.ppSecurityGroup` (0.51) on top of the DRep thresholds — "DReps alone leave it sitting in the queue until it expires."
- **The deployed musashi config silences the entire transaction-arrival path, while fully tracing the Leios path** (verified 2026-09-21 by running `cardano-node trace-documentation` with the w36 binary against the pinned config — 650 namespaces, 143 metrics; layer: deployed configuration): every `TxSubmission.TxInbound.*`, `TxSubmission.Remote.*`, `TxSubmission.Local.*` and `TxSubmission.TxOutbound.*` namespace is `Debug`/`Info` and reported **Invisible** against the config's `Notice` filter; `Mempool.AttemptAdd` and `Mempool.SyncNotNeeded` are explicitly `Silence`d (so the mempool accept-rate *denominator* is off while `AddedTx`/`RejectedTx` are on); and the four Leios namespaces run at `Debug` with `maxFrequency: 0`. Collecting push/pull data therefore requires a config edit and restart, not just analysis.
- **`Consensus.LeiosKernel.BodyHits` already instruments per-EB transaction provenance** (verified 2026-09-21 at consensus `b56977b`, table present at `7abeda65`): emitted once per EB body inserted into the TxCache and deliberately deferred until after the mempool pull, it carries `txsInEb`, `tracked`, `acquired`, `validated`, `mempoolHits`, `missedBoth`, `cacheTxCount`, `cacheLoad`, with the documented nesting `txsInEb ≥ tracked ≥ acquired ≥ validated`. So cache share, mempool share, and pull share per EB need no new instrumentation — only enabling collection. It is per **EB**, never per transaction: which transactions came from where is not traced.
- **No `leios*` metric is registered in the node's documented metric set** (verified 2026-09-21 from `--output-metric-help` and `--output-namespace-list` on **both** the w36 and w38 binaries; layer: implementation): the Leios tracers emit at runtime (`Consensus.LeiosKernel.Db` appears in node logs) but no Leios namespace or metric appears in either generated inventory, and the only metric names the Leios code declares at all are the eight `leiosFetch{Body,Txs}*Bytes` counters plus the `leiosDb*` gauges. **This answers the standing question about `leios_logmetrics_*`: no such metric exists in these builds.** Whether the declared ones reach the Prometheus endpoint is untested here and settled by `curl -s localhost:12798/metrics | grep -i leios` on a running node ❓.
- **`cardano-node trace-documentation` is the authoritative instrumentation inventory, and it is config-aware** (verified 2026-09-21): given `--config`, it reports per namespace the severity, the backends, and whether the trace is `Visible`/`Invisible` *under that config* — turning "which traces will I actually get" from a source-reading exercise into one command. The w36-vs-w38 diff is exactly one namespace (`Mempool.CapacityChanged`) and one metric (`mempoolCapacityBytes`).
- **The `BlockPointMissing` warning is unconditional and does not indicate anything missing** (verified 2026-09-21 by source reading at consensus `b56977b` **and** at `7abeda65`, the rev the w36 build the network runs was pinned to — identical code, same line 958): in [`LeiosDemoLogic.hs:958`](https://github.com/IntersectMBO/ouroboros-consensus/blob/b56977baae0740f563060a8a9171c78be865b357/ouroboros-consensus/src/ouroboros-consensus/LeiosDemoLogic.hs#L958) `traceWith ktracer $ TraceLeiosBlockPointMissing point` sits inside the novel-body branch with **no test of whether the point is present**, one line before the idempotent `leiosDbInsertEbPoint`. So it fires once per novel, not-too-old EB body — it is an EB-acquisition counter wearing a warning's name, and its rate should track `LeiosBlockAcquired` (traced a few lines later in the same block) one-for-one. It is `LSWarning` severity while `BlockAcquired` is `LSInfo`, which is why it stands out in a log. The FIXME above it ("the point MUST already be present here … announcement handling inserts it") describes intended behavior: **`leiosDbInsertEbPoint` has exactly one production call site — this one** — so the announcement path does not insert EB points at all, and the `ebs` table is populated solely on body acquisition. A third stale comment for the collection: the function's own haddock in `LeiosDemoDb/Common.hs:77` says it is "Called on the announcement path (forge issuing an EB, peer receiving an announcement)", and `leiosDbInsertEbBody`'s says "The point MUST already have been inserted via `leiosDbInsertEbPoint` (announcement path)".
- **The LeiosDb is queryable SQLite, and EB overlap is a local SQL query** (verified 2026-09-21 by source reading at consensus `b56977b`; layer: implementation): WAL mode, tables `ebs(ebSlot, ebHashBytes, ebBytesSize, missingTxCount, status)`, `ebTxs(ebHashBytes, txOffset, txHashBytes, txBytesSize)`, `txs`, `ebsMissingTxs`, `gcTxCandidates`. So the kleioscan "tx duplication" metric is computable on one's own relay with `SELECT COUNT(DISTINCT ebHashBytes) … GROUP BY txHashBytes` — subject to it being one node's GC-truncated, diffusion-dependent sample. **No vote or certificate tables exist**: vote state is in-memory only, so votes and quorum formation are trace-only.

- **A single VRF win crashed block producers network-wide on musashi** (Red Team, #team-leios 2026-09-02; layer: deployed network, measured): an EB forged with 8 fake transactions — a CBOR `array(4)` whose first element is 250 random bytes where a transaction-body map belongs — passed the fetch-time hash check, diffused as a *certified* EB to **60+ distinct peer IPs**, and then killed every Haskell block producer that unpacked it on `DecoderErrorDeserialiseFailure "Leios Tx"` at `Shelley/Ledger/Leios.hs:308`. IOG block producers were offline for the ~10-minute attack window; relays were unaffected and systemd restarted the producers. In the red team's own words, "some (but not a lot of) stake is required… one VRF slot is enough." Independently found by the audit as **LEI-001**. - **Two protocol-level adversary results carry numbers** (#team-leios, 2026-09; layer: simulation and analysis, not measured on the deployed network): Karl Knutsson's **leeching / cold-EB** analysis has a passive attacker failing above **50 Mbps** egress for a 12 MB EB, certifying a cold 12 MB EB requiring ~**250–300 MB/s**, and resisting a leeching attacker that also downloads from the honest 25% pushing the requirement above **250 Mbps** (2026-09-17). By contrast **T23 (withhold-then-burst) showed no measurable harm** up to 100 EBs / 3.6 h stale / 150 ms links — the pull-based EB fetch self-regulates (Christopher Tilt, 2026-09-06, preliminary).
